# Repository Guidelines

## Project Structure & Module Organization

This is a pnpm monorepo. `apps/web` is the React application: `src/App.tsx` owns navigation, the session gate and global data actions, and `src/Production.tsx`, `src/LotDrawer.tsx`, `src/MonthEnd.tsx`, `src/Shipments.tsx`, `src/Settings.tsx` and `src/Users.tsx` contain the operational views and editors. `src/api/` is the only code that talks to the server: `client.ts` sends every request (the CSRF header, typed errors, and sign-in again after a 401), `mappers.ts` converts the API's JSON to the domain shapes the screens use, `queries.ts` holds the TanStack Query hooks and their keys, and one file per area holds the writes, each followed by a refresh of the queries it affects. The sign-in screen (Google, and the backup admin's password) and the profile card are in `src/auth/`, new-record defaults in `src/drafts.ts`, the signed-in user's permissions in `src/access.ts`, shared primitives in `src/ui.tsx`, and global styles in `src/index.css`.

`packages/domain` holds the rules shared by the browser and the server: domain types in `src/models.ts`, date and quantity rules in `src/calculations.ts`, field validation in `src/validation.ts`, and role permissions in `src/permissions.ts`. `src/api.ts` holds the API's JSON shapes; `apps/api/src/contract.ts` checks at compile time that the server's views produce exactly them, so a changed response fails `pnpm typecheck`. The web app imports the package directly.

`apps/api` is the Express API. `src/app.ts` builds the app, `src/server.ts` starts it, `src/core/` holds shared middleware and the Prisma client, and `src/modules/<area>/` holds one folder per business area. `prisma/schema.prisma` and `prisma/migrations/` define the PostgreSQL schema, and `prisma/grants.sql` sets the app role's privileges after every migration. Every API route starts with `publicRoute()`, `requireSignedIn()` or `requirePermission(action)` from `src/core/access.ts`. `src/api.test.ts` fails for a route without one, and holds the table of every route and its permission, so add a row with each new route. Integration tests use `createTestDatabase()` and the fixtures in `test/support/`. Record modules (`lookups`, `products`, `lots`, `rm-batches`, `grn-receipts`, `activity`) lock the lot row before any change to a lot or its entries (`modules/lots/lot-lock.ts`), resolve dropdown ids with `resolveLookups`, run the shared `@boat/domain` validators, and write history with `recordActivity` in the same transaction. Lot reads map rows to the domain's shapes in `modules/lots/lot-view.ts`, so computed fields come from the same functions as the browser. An integration test that pins a functional requirement starts its title with the id (`FR-4.2 …`); `src/fr-coverage.test.ts` checks every one is covered. `shipments` follows the lots pattern (row lock, version, `validateShipment`, history), with ETA revisions written as the demo's `saveShipment` does. `reports` builds the month-end summary with the domain's `monthSummary`. A lot is complete once its actual date is set (`completed_on` mirrors `actual_date`). `grn-receipts` is mounted only when `FEATURE_GRN` is on (off by default), and the web app hides GRN through `features` in `/auth/me`; rework and fresh production are hidden and never written. `auth` signs staff in with Google (`google.ts`): only users an admin has added, with an address on `GOOGLE_ALLOWED_DOMAINS`. The one backup admin (`password_login`) signs in with a password, set by `create-admin`; there are no invite or reset links. `data-transfer` exports and imports the demo's backup format; backup validation lives in `@boat/domain/backup`, shared with the browser, so tighten it there.

`e2e` is the Playwright suite. Global setup starts Postgres with Testcontainers, runs the built API serving the built web app on one origin, and starts `packages/oidc-stub` in place of Google, signs the admin in with the password `create-admin` prints, and adds one user per role who then signs in through the stub. Every test resets the data first (`support/test.ts`), seeds what it needs through the API (`support/seed.ts`), and runs on desktop Chromium and at 390 × 844. Specs never sign out, disable or change the password of the four seeded users; a test that needs to uses `newUser()`.

## Build and Development Commands

Use Node 24 (`nvm use`) and pnpm (`corepack enable`). Run `pnpm install` once. `pnpm typecheck`, `pnpm test`, `pnpm format:check` and `pnpm build` run across all packages. To run the app, copy `apps/api/.env.example` to `apps/api/.env`, start Postgres with `docker compose up -d db`, apply migrations and grants with `pnpm --filter @boat/api db:migrate`, and create the backup admin with `pnpm api create-admin --email <address> --name <name>`, which prints a password once (rerunning it makes that address the backup admin and sets a new password). Everyone else signs in with Google: set `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` and `GOOGLE_ALLOWED_DOMAINS` as `.env.example` describes, and add them under Settings → Users. Then run `pnpm --filter @boat/api dev` and `pnpm dev` side by side; Vite proxies `/api` to the API on port 3000, so cookies stay same-origin as on Render. `pnpm --filter @boat/api test:int` runs the database tests and `pnpm e2e` the Playwright suite against the output of `pnpm build` (both need Docker; run `pnpm --filter @boat/e2e exec playwright install chromium` once).

## Coding Style & Naming Conventions

Use strict TypeScript and functional React components. Keep storage, calculations, and presentation separate. Use PascalCase for components and model interfaces, camelCase for functions and fields, and descriptive feature names for files. Preserve ISO `YYYY-MM-DD` strings for date-only business rules. Run `pnpm format` for Prettier's two-space, single-quote, no-semicolon style. Tailwind utility classes and the reusable primitives in `ui.tsx` provide consistent controls and focus states.

## Verification Guidelines

Business rules are unit-tested in `packages/domain` (`pnpm --filter @boat/domain test:coverage` must stay at or above 95% line coverage). API behaviour is tested with Supertest, and the database with Testcontainers. CI runs all of them. The Playwright suite covers every user flow, on both viewports; change or add a spec in `e2e/tests` with each change to a screen. The web app's unit tests (`pnpm --filter @boat/web test`) cover the API client and mappers.

## Commits and Pull Requests

The workspace has no usable Git history, so no established commit pattern can be inferred. Use short imperative subjects such as `Add shipment ETA history`. Pull requests should summarize affected flows, list manual verification, link relevant issues, and include screenshots for visual changes. Do not include generated `dist/` or `node_modules/` files.
